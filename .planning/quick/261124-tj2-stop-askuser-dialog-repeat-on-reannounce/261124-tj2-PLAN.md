<objective>
Stop the ask-the-user dialog from re-opening every 20 seconds while the user is
still reading it: a live re-announce dedupe entry must have its TTL refreshed by
each joined re-announce, so one `interaction/requestUserInput` ask renders as ONE
ACP form elicitation for as long as the app-server keeps re-announcing it.

Field evidence (2026-11-24, Orca journal `agent-session-domain.db`, table
`journal_items`, session `19467492-c156-4cd1-b922-17cef726fd11`): the same
"Complete the milestone?" ask was recorded as 15 separate `elicitation/create`
requests in one turn (request ids `…:688`–`…:702`), and another ask as 15 more
(`…:29`–`…:43`). The request ids are contiguous and the item creation times are
25 s apart once, then exactly 20 s apart (04:27:30 → 04:27:55 → 04:28:15 →
… → 04:32:15; 01:18:55 → 01:19:20 → 01:19:40 → …). 20 s is exactly
`RouterDefaultDeadline` (15 s) + `dedupeGrace` (5 s) — the TTL
`dedupeTTL(0)` computes for the `interaction/requestUserInput` policy row,
whose `Deadline` is deliberately 0 ("a human answering a dialog takes
minutes", responder.go:313-320). While the entry is alive a re-announce
joins and parks; after the TTL expires the next re-announce is treated as a
fresh primary and runs `handleUserInput` again → another elicitation → another
dialog.

Purpose: the two knobs disagree — the handler is unbounded while the dedupe
entry is capped at the router default. Refresh the entry on join, so the
existing backstop stays for a wedged primary whose re-announces stopped, but
a dialog that is still being re-announced never expires.

Output: the refresh-on-join behavior with fake-clock unit tests that fail on
the current code (a re-announce after the original TTL but within the
refreshed TTL must join, not start a second handler), the updated dedupe
comments, and one sentence in the dialect doc's requestUserInput row that
makes the one-dialog guarantee explicit.
</objective>

<context>
Current implementation (verified at branch base `244a7c6` / master
`398ceaf`):

- `internal/interact/dedupe.go:68-83` — `dedupeTable.claim`: sweeps, looks up
  `(method, params.requestId)`, and on a join returns `true` WITHOUT touching
  the entry's `expires`; only a fresh primary stores
  `dedupeEntry{expires: now.Add(ttl)}`.
- `internal/interact/dedupe.go:92-102` — `release` replaces the pending entry
  with a resolved tombstone whose `expires` is `now + resolutionGrace` (2 s);
  a tombstone must not be refreshed by later re-announces, or it would never
  be swept.
- `internal/interact/dedupe.go:132-140` — `dedupeTTL`: `deadline <= 0` falls
  back to `zcode.RouterDefaultDeadline` (15 s, internal/zcode/conn.go:32) and
  adds `dedupeGrace` (5 s) so no entry is immortal.
- `internal/interact/responder.go:243-262` — the Serve join arm: a joined
  re-announce parks on `<-ctx.Done()` and stays silent (the first reply
  resolves the whole pending set server-side).
- `internal/interact/responder.go:313-320` — the requestUserInput policy row
  with `Deadline: 0`.
- No `internal/interact/dedupe_internal_test.go` exists; the only end-to-end dedupe
  coverage is the `reannounce-dedupe` fake scenario (`internal/interact/
  responder_test.go:34`, 40 ms interval × 2) which always lands well inside
  the TTL and therefore never exercised an expiry-then-rejoin cycle.

Why refresh-on-join rather than an infinite TTL: the map's bound stays one
entry per distinct `params.requestId` either way, but refresh keeps the
original "backstop for a primary wedged past its own deadline" semantics —
after the server stops re-announcing (resolved or client gone), the entry
dies `ttl` later. An immortal entry (TTL 0 / 24 h) would drop that backstop.

Constraints: do not change the wire shapes, the re-announce parking
semantics, `release`/`resolutionGrace`, the other policy rows, or the
`Deadline: 0` decision for requestUserInput. Never refresh a resolved
tombstone.
</context>
