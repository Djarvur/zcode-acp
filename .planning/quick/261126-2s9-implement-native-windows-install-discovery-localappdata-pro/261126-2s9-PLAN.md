<objective>
Give the Windows port native install discovery so `--app-server`/`ZCODE_ACP_APP_SERVER` becomes optional, with seam-driven tests that run on the existing Linux gate and windows-tagged tests that prove the production wiring.

Purpose: the Windows port currently answers the install stage with a single stub row that tells the user to pass the install path, so every Windows user must hand the wrapper one. The documented Windows install locations (per-user %LOCALAPPDATA%\Programs\ZCode, per-machine %ProgramFiles%\ZCode, and the uninstall-registry records) are stable, readable facts; discovering them natively removes the only mandatory Windows setup step while keeping the honest-empty-result contract.

Output: a platform-neutral Windows install stage fed by injectable seams, the Windows production wiring (environment directory sources + read-only registry enumeration) behind the windows build tag, unit tests that execute on Linux, windows-tagged wiring/integration tests, and a README that documents the new default.

TDD applicability: yes for Task 1 (pure path/string rules and the seam-fed stage have exact expected outputs); Task 2 is a windows-tagged wiring suite and compiles under the local cross-target gate; Task 3 is documentation with structural verification.

Locked design (follow it; do not re-invent the seams):

- Precedence stays exactly as the Linux stage: `Discover` runs the override probe first, then the platform install stage, then the builtin-runtime and builtin-bundled rows. The Windows stage must not change `discover.go`'s ordering code — it only supplies rows and at most one winning Install.
- Native Windows order (first match wins, all rows still recorded): `%LOCALAPPDATA%\Programs\ZCode` (layout `windows-user`) → `%ProgramFiles%\ZCode` (layout `windows-machine`) → `%ProgramFiles(x86)%\ZCode` when set and different (layout `windows-machine`) → the uninstall-registry records in fixed hive order HKCU, HKLM 64-bit view, HKLM 32-bit view (layout `windows-registry`). Rationale: user-level installs win over machine-level ones, mirroring the Linux user-entry-before-system-dir rule; the registry is last because it only adds records that the directory probes could not reach (custom InstallLocation).
- Only one `windows-install` row exists: the not-consulted row emitted when an earlier probe (the override) already won. Directory sources each get their own stable row name (`windows-localappdata`, `windows-programfiles`, `windows-programfiles-x86`), so diagnostics stay readable.
- Registry rows: one `windows-registry` summary row (scanned count, matched count, partial-error note) plus one `windows-registry-entry` row per ZCode-matching record (Query = the full registry key path, Result = miss reason or found root + version). Records whose DisplayName does not name ZCode produce no row — the uninstall hive holds hundreds of unrelated products and the rows must stay actionable.
- The Windows validation surface is the same invariant tree as every other layout: `<root>\ZCode.exe` and `<root>\resources\glm\zcode.cjs` (the relative entrypoint path is layout-invariant, install-discovery.md :38). Nothing from the registry is executed, PATH-resolved, or shell-interpreted — the strings only become candidate roots.
- Override and builtin behavior are untouched: `OverrideInstall`, `Probe`, `Discover`, `emptyResultError`, `probeBuiltinRuntime`, `probeBuiltinBundled`, `Mount` and every other platform file keep their behavior.
