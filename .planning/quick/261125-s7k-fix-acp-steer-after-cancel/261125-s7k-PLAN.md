<objective>
Answer `session/cancel` deterministically so a client steer can start.

Orca's steer is not a mid-turn prompt. `AcpStructuredTurns.dispatch` (Orca
1.4.274, `src/main/acp/turns/acp-structured-turns.ts`) queues the new send,
calls `cancelForSteer()` → `session/cancel`, and dispatches the new prompt only
from `finish(send)`, which runs when the ACTIVE `session/prompt` request
settles. Its source comment states the rule: "Steers wait for the active prompt
to answer cancellation." A wrapper that leaves the cancelled prompt unanswered
leaves the steer held forever: the current answer is interrupted, the new one
never starts.

Field evidence (2026-11-25, Orca journal `agent-session-domain.db`, session
`8c4ebde4-a310-4627-8da2-a791dc87a939`): the last submission is recorded at
17:36:06Z and its turn starts; the user steers shortly after; no later
`journal_submission_attempts` row exists — the steer never reached dispatch,
because the active prompt never answered.

Current mechanics (verified at branch base `74016b7`):

- `internal/turn/machine.go:365-383` (`Cancel`) transitions running → cancelling
  and sends `session/stop` on the bypass lane; the resolution itself is
  signal-driven only.
- `internal/turn/machine.go:401-447` (`ObserveEnvelope`) classifies terminals
  first; `classifyTerminalLocked` (:630-671) maps `turn.failed` to `StopFailed`
  unconditionally — so on the real desktop, whose cancel outcome IS
  `turn.failed` (field log 17:20:29.181: "the prior turn emitted turn.failed
  (cancelled)"), the front answers the cancelled prompt with `-32603`, not
  `stopReason:"cancelled"`.
- The only other resolution paths while cancelling are the cancelled idle patch
  (`classifyIdlePatchLocked`, :582-618) and the quiet settle
  (`onWatcherObservation`, :501-533). The quiet settle fires only after
  `FloorMultiple x QuietMs` (7.5 s) from the send ack and then `QuietMs` (2.5 s)
  without watched-session activity (`internal/turn/watcher.go`): a stop landing
  early in a turn, or any backend chatter after it, keeps the prompt open well
  past the client's steer window — indefinitely if activity never stops.

Purpose: make the cancellation outcome ACP-correct and bounded. A cancel is
the client's explicit demand; the answer is the turn's cancellation, and the
machine must not depend on a backend signal to say so.

Output: the failed-terminal-while-cancelling mapping, a configurable cancel
grace that resolves `StopCancelled/SignalCancel` when no signal arrives, the
front wiring for both machine construction sites, an end-to-end steer
regression over the composed fake back leg, and one doc paragraph stating the
cancel-answer guarantee.
</objective>

<context>
Design decisions:

- Failed terminals while cancelling map to `StopCancelled/SignalCancel`.
  `turn.failed`, and `turn.terminal` with a failed/error status, are exactly
  the stop's observed outcome once the client asked; reporting `StopFailed`
  turns the answer into `-32603`, which is neither the ACP cancel contract nor
  dispatches the client's steer queue. A `turn.completed` (or an idle patch
  leaving running with a non-cancelled status) is left alone: the turn really
  completed, and a racing cancel must not rewrite that fact (PITFALL 4's
  "never lie about how the turn ended" holds in both directions).
- The cancel grace is a backstop, not a replacement: the terminal, the idle
  patch, and the quiet settle stay the primary signals. The grace only fires
  when the turn is still `stateCancelling` and unresolved after the configured
  interval; it resolves `StopCancelled/SignalCancel` with a nil error, which is
  the honest client-requested outcome, and the backend's late signals are then
  ignored by the existing exactly-once path.
- Default grace: 2 s. The live stop→terminal latency observed in the field log
  is ~300 ms (17:20:28.882 stop received → 17:20:29.181 turn.failed), so 2 s
  keeps a 6x margin while answering far inside a person's steer interaction.
  The value is a seam (`turn.WithCancelGrace` / `acpfront.WithCancelGrace`) so
  tests run in milliseconds; production wiring sets nothing and takes the
  default.
- One shared front construction helper for `NewSession` and
  `resumeSessionLocked` keeps the seam from diverging between new and resumed
  sessions (the same failure mode the completed stall-recovery plan documents).
- Out of scope: the orphaned-backend `-32010` retry policy, the no-progress
  watchdog, and terminal/idle turn binding — those belong to the separate,
  already-planned quick task `261125-r6o`. This task changes only the cancel
  answer path: no wire vocabulary, no busy contract, no corpus goldens.
- Do not touch the `send-refused-32010` / `cancel-mid-turn` corpus rows or
  goldens; the new scenario is additive.

Constraints: no new dependencies; the existing single-active-turn invariant,
the front-owned turn context, the bypass-lane stop, the flush-before-stopReason
release order, and the "no content in logs" rule all stay intact; gofmt, vet,
golangci-lint, and `-race` clean.
</context>
