<objective>
Carry the plan-approval decision literal through the ask-the-user bridge.

ZCode's ExitPlanMode emits `interaction/requestUserInput` with
`schema: {interaction: "plan_approval", toolName: "ExitPlanMode"}` and one
question whose option is `{value: "approve", label: "Approve", description:
"Exit plan mode and start implementation."}`. The bridge currently drops the
option value at decode and always renders `Const: o.Label`, so an ACP client
can only answer "Approve". The backend's `normalizePlanApprovalAnswer` reads
`content.answers[<question text>]`, trims it, and grants `decision: "allow"`
only for the exact literal `approve`; "Approve" falls into the deny path with
`reasonSource: "plan_approval_feedback"` — the reported failure.

Purpose: make the plan-approval round-trip decision-correct without changing
the ordinary AskUserQuestion label contract.

Output: `UserInputOption.Value` and `UserInputAsk.Interaction` on the neutral
ask, a plan-approval-aware enum const in `BuildElicitationRequest`, a
plan-approval-aware answer normalization in `MapElicitationOutcome`, and
locked tests for decode, build, map, and the composed asker path.
</objective>

<context>
Design decisions:

- Two identities, one discriminator. Ordinary asks keep label identity end to
  end (const = title = label; the answer is the selected label, which the
  broker merges into the AskUserQuestion tool input). Plan approval uses value
  identity: the enum const is the wire `value`, the title is the display
  label, and the accepted string maps back to the value. `schema.interaction`
  is the only discriminator — no toolName sniffing, so an ordinary ask that
  happens to run under a tool named ExitPlanMode stays on the label contract.
- The value fallback is honest: when the wire omits `value`, the option's
  identity is its label. Plan approval then renders const = label and the
  answer is the label, which is the only string the client could have seen.
- Normalization matches both strings a client may return (the enum Const and
  the Title) against each option's value-then-label, and passes anything else
  through verbatim — never synthesize "approve" from an unrecognized answer.
- The answer stays keyed by question text in `answers`; `internal/interact`'s
  `acceptAnswer` already nests that map under `content.answers`, which is the
  first key `normalizePlanApprovalAnswer` reads. No responder change, no
  `content.answer`/`content.answer_0` compat slot needed.
- Multi-select shares the option slice and the same normalization per element
  (plan approval is single-select today, but the shared code must stay
  coherent — no arm that silently keeps label identity).
- Docs note (deliberately out of scope): the dialect row's "options
  value=label per mapAskUserQuestion" parenthetical describes the upstream
  AskUserQuestion mapping and remains true for ordinary asks. This quick task
  changes only the acpport files; a dialect-doc sync for the plan-approval
  exception is a separate doc change.
- Scope: only `internal/acpport/userinput.go` and its internal test file.
  Adding struct fields is source-compatible with `internal/interact` and
  `cmd/zcode-acp`, which construct/consume the types without field ownership.

Constraints: no new dependencies; no SDK type leaks outside `internal/acpport`;
keep the free-text (no-questions) arm and the decline/cancel pass-through
exactly as they are; the strict golangci-lint gate (default: all) must pass —
hoist repeated test literals (goconst), keep blank lines before returns
(nlreturn), and respect the 120-column limit.
</context>
